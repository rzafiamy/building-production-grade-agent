*PART II — ARCHITECTURE FUNDAMENTALS*

## Chapter 9 — Compression: The Hidden Challenge

> *"You can't fight the context window. You can only manage it — or be managed by it."*

> [!NOTE]
> **Chapter Goal:** By the end of this chapter, you will understand why context compression is necessary, the fundamental trade-offs between different compression approaches, when each strategy is appropriate, and how to select and configure compression strategies in Lemura.

---

### 9.1 Why Compression Is Inevitable

The context window is finite. Agent sessions are not. As discussed in **Chapter 7 — Context: The Agent's Working Memory**, context grows monotonically with turns. At some point, every long-running agent session will either hit the context limit or require active management to stay within it.

The naive responses to this — use a model with a bigger context window, or truncate when full — both fail in production. Bigger windows push the problem further out while increasing per-call cost. Truncation discards information with no regard for what the session still needs. Both approaches eventually produce sessions that fail or produce wrong results.

Compression — the deliberate reduction of context size while preserving the information necessary for session continuity — is the only sustainable response. It is not a debugging tool you reach for when things go wrong; it is architecture you design in from the start.

The hidden part of the challenge is that compression is always lossy. You cannot compress a 10,000-token tool result to 500 tokens without losing information. The engineering problem is making those losses deliberate and tolerable, not random and catastrophic.

### 9.2 The Compression Spectrum

#### 9.2.1 No Compression: Works Until It Doesn't

The simplest approach is no compression: accumulate context until the session ends or the window fills. For short sessions with bounded tool use — under 20 turns with modest tool results — this works reliably and requires no configuration.

The problem is predictability. A session that runs in 15 turns 99% of the time will eventually run in 40 turns when the user gives an unusually complex input. Without compression, that session fails at the context limit. With compression, it degrades gracefully. Use no-compression only for sessions with rigorously bounded maximum lengths.

#### 9.2.2 Truncation: Brutal and Simple

Truncation removes the oldest messages from the conversation history when the context exceeds a threshold. It is O(1) to implement, adds no latency, and requires no LLM calls. It is also the most destructive approach.

Everything removed is gone. If a critical tool result from turn 2 gets truncated when the session reaches turn 25, the model no longer has access to it. If the original user instructions included specific requirements that are now gone, the model cannot meet them. Truncation treats all messages as equally disposable, which they are not.

Truncation is appropriate as a final safety net — the strategy that fires if all other strategies fail or are not configured. Never use it as the primary compression strategy for sessions that span more than 30 turns.

#### 9.2.3 Rolling Summaries: Lossy but Cheap

Rolling summaries periodically summarize the oldest N turns into a single summary message, discarding the originals. The summary is generated by the model, capturing key facts and decisions at a fraction of the original token count.

The cost is an LLM call — latency and token expense — each time a compression event fires. For sessions that compress infrequently (every 20 turns), this is negligible. For sessions that compress every 5 turns, the overhead accumulates. Profile your expected compression frequency before committing to this approach.

Information loss in rolling summaries is content-dependent. Summaries reliably preserve: key facts discovered, decisions made, conclusions reached. They often lose: the exact format of tool outputs, minor details that seemed unimportant at compression time but become important later, the precise wording of earlier instructions.

#### 9.2.4 Selective Preservation: The Sandwich Pattern

The sandwich pattern preserves the beginning and end of the conversation history while summarizing the middle. The "bread" — the first and last N turns — is kept verbatim. The "filling" — everything in between — is summarized.

This pattern exploits the attention distribution of language models: models attend more strongly to content near the beginning and end of the context. The system prompt and the earliest turns (which typically contain setup and critical instructions) are preserved at the beginning. The most recent turns (which contain the current state of the task) are preserved at the end. The middle history — which the model would attend to least anyway — is the candidate for summarization.

The sandwich pattern preserves more critical information than rolling summaries at the cost of slightly higher implementation complexity. For most long-running agents, it is the right default.

#### 9.2.5 External Memory: Expensive but Lossless

External memory offloads information from the context window to a persistent store (a vector database, a key-value store, a structured database) and retrieves it on demand. Unlike summarization, retrieval is theoretically lossless — the full content is preserved in storage and can be fetched when needed.

The engineering cost is high: you need embedding generation, a vector search system, retrieval quality evaluation, and the added latency of retrieval on every turn. It is also not truly lossless in practice, because retrieval fails when the query does not match the stored content well. The session must be designed to issue retrievals at the right time.

External memory is appropriate for sessions that span multiple user interactions, sessions that must reference a fixed document corpus, or systems where session continuity over days or weeks is a requirement. It is overkill for bounded single-session tasks.

### 9.3 What to Compress and What to Preserve

#### 9.3.1 Sacred Context: Never Compress

Some content should never be compressed or removed from the context. System prompt: it contains the agent's operating instructions. The current goal: without it, the model loses direction. The most recent few turns: they contain the current state of the task. The current user message: it is what the model is currently responding to.

Sacred content belongs in positions that compression strategies are configured to leave alone: the very beginning (system prompt) and the very end (recent turns). Compression strategies in Lemura are configured with explicit preservation counts (`preserveFirst`, `preserveLast`) that implement this protection.

#### 9.3.2 Compressible Context: Middle History

The middle of the conversation history — turns more than N positions from the end — is the primary compression candidate. These turns contain the detailed record of what the agent has done, but the model needs the outcome of that work, not the blow-by-blow account.

A tool call from turn 5 that discovered a list of files is more compressible than the result of the tool call from turn 24 that is directly informing the current turn's reasoning. The further back in history, the more compressible; the more recent, the more sacred.

#### 9.3.3 The Sandwich Pattern Visualized

```text
┌─────────────────────────────┐
│    SYSTEM PROMPT (sacred)   │
├─────────────────────────────┤
│    GOAL + PLAN (sacred)     │
├─────────────────────────────┤
│                             │
│   [ COMPRESSED SUMMARY ]   │  ← rolling summary of old turns
│                             │
├─────────────────────────────┤
│   RECENT TURNS (preserved)  │  ← last N turns verbatim
├─────────────────────────────┤
│   CURRENT INPUT (sacred)    │
└─────────────────────────────┘
```

This structure ensures that the model always has access to its operating instructions (top), a summary of what has been done (middle), the most recent context for immediate reasoning (bottom of history), and the current input. Information is lost in the summary but replaced by a semantically equivalent representation at lower token cost.

### 9.4 Compression Quality: What Gets Lost

#### 9.4.1 Information Loss Is Unavoidable

Every compression strategy that does not use external storage loses information. The question is not whether information is lost — it always is — but whether the lost information was needed for session continuity. A well-designed compression strategy loses information that would not have been needed anyway. A poorly designed one loses information that breaks the session.

The most common critical information loss: exact file paths or identifiers that will be used in later tool calls (summarized as "a configuration file" rather than "/etc/app/config.yaml"), specific numerical values (summarized as "a large dataset" rather than "2,847 records"), and early instructions that were important but not recently restated.

Design your goal injection strategy to keep the most critical facts visible outside the compressible history: file paths discovered early should be recorded in the goal's sub-goal completion notes, key facts should be called out in the goal block, and decisions should be summarized with enough precision to be actioned.

#### 9.4.2 Measuring Compression Quality

Compression quality can be measured by running the same session twice: once without compression and once with compression, then comparing the final outputs. If the compressed session produces the same result as the uncompressed session, the compression preserved the information needed for the task. If the outputs diverge, the compression is losing something critical.

This is an integration test, not a unit test. Run it on representative tasks for your agent's domain. Compression that works well for research tasks may fail for tasks that require precise multi-step file manipulation.

#### 9.4.3 When Bad Compression Breaks the Agent

Bad compression produces a specific class of failure: the agent appears to be running correctly — tool calls are well-formed, reasoning is coherent — but the output is wrong because the agent is working from an incomplete or inaccurate summary of earlier work. This is harder to detect than an error-termination failure because there is no error signal.

The detection mechanism is semantic evaluation of the output, not syntactic validation. An agent that forgets a key file path due to compression and writes to the wrong location will complete successfully with a wrong result. Only comparing the output against the expected result reveals the failure. This is why evaluation infrastructure — covered in **Chapter 35 — Continuous Improvement and Evaluation** — is not optional for production agents.

### 9.5 The Cost of Compression

#### 9.5.1 Every Summary Is an LLM Call

`SandwichCompressionStrategy` and `HistoryCompressionStrategy` both generate summaries by calling the model. Those calls cost tokens and add latency. A compression event that generates a 300-token summary from 3,000 tokens of history costs a few cents and adds 1–3 seconds of latency to the turn where it fires.

At low frequency — compressing once every 20 turns — this cost is negligible. At high frequency — compressing every 5 turns — it adds up. Measure the compression frequency for your typical session and verify that the added cost and latency are acceptable for your use case.

Using a smaller, cheaper model for summarization (rather than the session's main model) can significantly reduce compression cost without affecting quality. Lemura's compression strategies accept the adapter as a constructor parameter, which means you can pass a cheaper adapter to the compression strategy while using a more capable model for reasoning.

#### 9.5.2 Balancing Compression Cost vs. Context Cost

The trade-off is between the cost of compression (LLM call, latency) and the cost of running without compression (higher context tokens per call, eventual context failure). For sessions with expensive main models, compression with a cheaper summarization model can reduce total session cost even after accounting for the summarization calls.

The break-even point depends on context growth rate and model pricing. For typical mid-tier frontier models and typical tool-heavy sessions, compression usually pays for itself within 5–10 turns of a session where it prevents context exhaustion. Calculate the break-even point for your specific model and tool configuration before concluding that compression adds cost.

### 9.6 Compression Strategies in Lemura

#### 9.6.1 `SandwichCompressionStrategy`

`SandwichCompressionStrategy` implements the selective preservation pattern. It fires when the context exceeds `triggerThreshold` (default 80% of `maxTokens`) and the number of turns exceeds `preserveFirst + preserveLast`. When it fires, it keeps the first `preserveFirst` turns and the last `preserveLast` turns verbatim, generates a summary of the middle, and stores it in `ctx.compressionSummary`.

```typescript
// Configuring SandwichCompressionStrategy with SummaryInjectionStrategy
import {
  SandwichCompressionStrategy,
  SummaryInjectionStrategy,
} from "lemura/context";

const session = new SessionManager({
  adapter,
  model: "gpt-4o-mini",
  maxTokens: 100_000,
  compressionStrategies: [
    // Always runs first: injects the accumulated summary into the context
    new SummaryInjectionStrategy({ priority: 1 }),
    // Fires at 80% of maxTokens, preserves 4 oldest and 10 newest turns
    new SandwichCompressionStrategy(adapter, {
      priority: 20,
      preserveFirst: 4,
      preserveLast: 10,
      triggerThreshold: 0.80,
      summaryMaxTokens: 500,
    }),
  ],
});
```

`SummaryInjectionStrategy` must be paired with any compression strategy that stores its output in `ctx.compressionSummary`. Without it, the summary is generated and stored but never injected into the context that the model sees.

#### 9.6.2 `HistoryCompressionStrategy`

`HistoryCompressionStrategy` summarizes the oldest `windowSize` uncompressed turns when the context reaches `triggerAtPercent`. It is a rolling-window approach: each compression event summarizes another window of old turns, accumulating the summary across multiple events.

```typescript
// Configuring HistoryCompressionStrategy for rolling summarization
import { HistoryCompressionStrategy, SummaryInjectionStrategy } from "lemura/context";

const session = new SessionManager({
  adapter,
  model: "gpt-4o-mini",
  maxTokens: 128_000,
  compressionStrategies: [
    new SummaryInjectionStrategy({ priority: 1 }),
    new HistoryCompressionStrategy(adapter, {
      priority: 30,
      windowSize: 8,         // summarize 8 oldest turns per compression event
      triggerAtPercent: 0.75, // fire at 75% of maxTokens
    }),
  ],
});
```

`HistoryCompressionStrategy` is less aggressive than `SandwichCompressionStrategy` — it compresses incrementally rather than all-at-once — making it a better choice for sessions where smooth, continuous compression is preferred over occasional larger compression events.

#### 9.6.3 `SummaryInjectionStrategy`

`SummaryInjectionStrategy` is not a compression strategy in the sense of reducing context size. It is an injection strategy: it takes the `ctx.compressionSummary` stored by a companion compression strategy and injects it as a synthetic system turn at the beginning of the turn list, ensuring the model sees the accumulated summary on every call.

Without `SummaryInjectionStrategy`, the summary generated by `SandwichCompressionStrategy` or `HistoryCompressionStrategy` lives in `ctx.compressionSummary` — a field in the context window object — but does not appear in the message array sent to the model. The summary exists but is invisible. Always pair compression strategies with `SummaryInjectionStrategy`.

#### 9.6.4 Configuring Priority and Trigger Thresholds

Strategies execute in ascending priority order. Lower numbers run first. The recommended configuration:

| Strategy | Priority | Why |
|----------|----------|-----|
| `SummaryInjectionStrategy` | 1 | Must run before compression, so the summary is visible before the call |
| `SandwichCompressionStrategy` | 20 | Runs after injection; compresses when threshold is reached |
| `HistoryCompressionStrategy` | 30 | Alternative to sandwich; runs later if both are configured |

Trigger thresholds should be set so that compression fires with enough headroom for the current turn's input and the model's output: at 80% of `maxTokens`, the remaining 20% must accommodate the current input, tool definitions, and the model's response. If your typical turn consumes more than 20% of `maxTokens`, lower the trigger threshold accordingly.

> [!WARNING]
> Do not configure `SandwichCompressionStrategy` without `SummaryInjectionStrategy`. Without injection, the model will not see the summary and will reason as if the compressed turns simply do not exist — producing inconsistent results that are very hard to diagnose. The pair is mandatory, not optional.

---

## Key Takeaways

- Compression is inevitable for any agent session longer than a few dozen turns; design it in from the start rather than reaching for it after the first context-exhaustion incident.
- Every compression strategy loses information; the engineering goal is to make those losses deliberate and tolerable, not random and catastrophic.
- The sandwich pattern — preserve first N turns, summarize the middle, preserve last N turns — is the right default for most long-running agents; it exploits the model's attention distribution to preserve what matters most.
- `SummaryInjectionStrategy` is mandatory when paired with any compression strategy that stores output in `ctx.compressionSummary`; without injection, the summary is generated but the model never sees it.
- Compression using a smaller, cheaper model for summarization can reduce total session cost compared to running without compression when the main model is expensive.
